## 🛠️ HTML 과제 회고

### 1. 웹 접근성(a11y)에 대한 고민: `ol`, `ul`에 항상 `aria-label`이 필요할까?

- **기본 요소의 역할 신뢰하기**: HTML의 기본 태그(`ol`, `ul`)는 그 자체로 이미 시맨틱한 의미(목록)를 지니고 있음.
- **무분별한 속성 추가 경계**: `aria-label`은 해당 요소의 목적이 명확하지 않거나 Screen Reader 사용자에게 추가적인 맥락 제공이 필요한 경우(예: Nav 영역 내 `nav aria-label="주요 메뉴"`, 동일한 태그가 여러 개 존재하는 경우)에 선택적으로 사용하는 것이 좋음.
- **인터랙션 중심의 접근성**: 상호작용(포커스)이 필요 없는 단순 정보 전달용 리스트(`li`)에 `tabindex`를 부여하지 않는 것이 오히려 키보드 사용자 및 스크린 리더 사용자의 탐색 피로도를 줄여준다는 것을 이해했음.

### 2. 데스크톱 환경의 `tel:`, `mailto:` 링크 동작 원리 파악

- **OS 및 브라우저 핸들러의 이해**: HTML 마크업 문제라기보다, 사용자 환경(OS/브라우저)에 해당 프로토콜을 처리할 기본 앱(Protocol Handler) 지정 여부에 따라 동작이 달라진다는 것을 수차례의 테스트(노가다)를 통해 확인했음.
- **Gmail 핸들러 설정**: `mailto:`의 경우 데스크톱 Chrome에서 Gmail 연결 설정을 통해 동작 검증이 가능함을 확인했음.

### 3. 관점의 전환과 모바일 실기기 테스팅 성공기 (Trouble Shooting)

1. **문제 정의**: 데스크톱 환경에서는 Skype나 휴대폰 연동 없이는 `tel:` 스키마를 실제 통화로 이어지게 테스트하기 어려움.
2. **관점 전환**: "데스크톱에서 억지로 통화 앱을 띄우기보다, 실제 전화 기능이 존재하는 **모바일 기기에서 직접 테스트**해 보자."
3. **새로운 장애물**: Node.js 기반 프레임워크 환경이 아니어서 `npm run dev --host` 같은 네트워크 바인딩 옵션을 사용할 수 없음.
4. **해결책 탐색 및 적용**:
   - VS Code의 **Live Server** 연동 방안 모색.
   - Stack Overflow 및 네트워크 지식을 활용해 터미널에서 `ipconfig` 실행.
   - 동일한 Wi-Fi 네트워크상에서 PC의 **IPv4 주소**와 Live Server 포트 번호(예: `http://172.x.x.x:5500`)를 조합해 모바일 브라우저로 접속 성공.
5. **최종 결과**: 모바일 실기기에서 `tel:` 링크 클릭 시 정상적으로 전화 앱이 호출되는 것을 직접 `검증함`.

### 🎯 회고 총평 (Takeaway)

- **접근성(a11y)에 대한 깊은 시선**: 단순히 규격을 맞추는 것을 넘어, "사용자가 이 요소를 만났을 때 어떻게 동작하고 느낄까?"를 고민하는 시각이 확장되었습니다. 또한 과도한 배려 즉 서비스내 모든 영역을 스크린리더블 하게 만드는 것은 오히려 사용자에게 피곤함을 유발시킬 수 있다는 깨달음(과유불급)을 얻었습니다.
- **관점의 전환, 유연한 사고**: 개발 도구의 제약에 막혔을 때, 문제의 본질(실기기 테스트)에 집중하여 네트워크 IP 접속이라는 우회 해결책을 찾아낸 뜻깊은 경험이었습니다.
